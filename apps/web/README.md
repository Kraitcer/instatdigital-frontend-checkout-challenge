# Checkout Web

React + TypeScript frontend для задания «Оформление заказа». Приложение работает с API из этого репозитория, хранит гостевую сессию и восстанавливает текущий заказ после перезагрузки страницы.

## Запуск

Из корня репозитория:

```sh
npm ci
npm run dev
npm run dev:web
```

API будет доступен на `http://localhost:4000`, фронтенд — на `http://127.0.0.1:5173`.

Сборка фронтенда:

```sh
npm run build:web
```

Если API запущен не на `http://localhost:4000`, передайте адрес через `VITE_API_URL`.

## Устройство API-кода

Все HTTP-запросы проходят через `src/api/client.ts`. В этом модуле задаются базовый адрес, `Authorization`, `Content-Type`, `Idempotency-Key`, сериализация тела, разбор `204`, чтение JSON, проверка HTTP-статуса и приведение сетевых, HTTP- и parse-ошибок к одному виду `ApiFailure`.

Компоненты не работают с `Response`, `response.ok` и сырым телом ошибки. Они вызывают функции из `src/api/checkout.ts`: каталог, корзина, расчёт, заказ, платёж и sandbox-карты. Компонент получает готовые данные или разобранную ошибку и отвечает только за отображение, сохранение формы и пользовательские действия.

Состояние сессии хранится через Redux Persist в `localStorage`: token, `orderId`, `paymentId` и ключи идемпотентности. При повторе запроса после потери ответа используется прежний ключ; после отказа или отмены оплаты новая попытка получает новый ключ. При ответе API `SESSION_INVALID` или `SESSION_REQUIRED` сохранённая сессия сбрасывается и создаётся новая.

Опрос оплаты находится в `PaymentPanel.tsx` и использует polling RTK Query только для незавершённого платежа. При размонтировании компонента подписка и polling прекращаются; завершённые статусы больше не опрашиваются, а кэш RTK Query применяет только актуальные результаты запроса.

## Проверенные сценарии

- Загрузка каталога, недоступный товар заблокирован.
- Добавление товара, изменение количества, удаление позиции и пустая корзина.
- Самовывоз с пунктом выдачи и курьерская доставка с адресом.
- Получение расчёта доставки и итоговой суммы от сервера.
- Создание заказа картой и наличными при получении.
- Выбор тестовой карты из API, успешная оплата, отказ банка и отмена.
- Повтор оплаты того же заказа после отказа или отмены.
- Восстановление сохранённого заказа и активной оплаты после перезагрузки.
- Обработка `CART_VERSION_CONFLICT`, `QUOTE_EXPIRED`, `CART_EMPTY`, сетевых ошибок и ошибок формы без очистки введённых данных.

## Обработка данных и стоимость

Частый участок — сопоставление каталога с корзиной при каждом рендере. `buildCartIndex` делает один проход по позициям корзины и строит `Map<productId, CartItem>`, затем один проход по товарам и разделяет их на доступные и недоступные. В карточке товара наличие позиции проверяется через `Map.get`, без повторного линейного `find` по корзине для каждого товара.

Такой вариант создаёт одну `Map` и два итоговых массива, не создаёт промежуточные коллекции через цепочки `map/filter`, не оставляет дырок в массивах и не копирует растущий аккумулятор на каждом шаге. Стоимость — `O(cartItems + products)` на рендер.

## Известные ограничения

Автотестов для браузерного сценария нет; основные проверки выполнены сборкой TypeScript/Vite и ручными сценариями через интерфейс.
